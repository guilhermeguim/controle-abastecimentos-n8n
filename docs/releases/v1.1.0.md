# Release v1.1.0

## Closing Date

2026-09-07

Local artifact checks are complete. Import and end-to-end execution in n8n were not performed during release preparation; the runtime checklist below remains available for deployment validation.

## Comparison Base

`v1.0.1..v1.1.0`

## Summary

- Type: MINOR; new protections and validation with the main flow and data model preserved.
- Scope: sender authorization, text-only input, stricter extraction, and export privacy.
- Workflow: 24 to 27 nodes.
- Database schema and SQL queries: unchanged; no migration is included.
- New configuration: the allowed Telegram sender must be set after import.
- Input restrictions: unmatched senders stop silently, non-text messages take a separate response path, and extracted fuels must belong to the declared enumeration.

## Changes From v1.0.1

| Area | Previous behavior | Updated behavior |
|---|---|---|
| Entry routing | Trigger directly normalized each message | Trigger first checks the sender and then non-empty text |
| Sender access | No sender gate in the workflow | `Usuário autorizado?` compares `message.from.id` with one configured ID; the false branch has no connection |
| Non-text input | No dedicated rejection path | Authorized non-text messages reach `Informar arquivo não suportado` and stop before SQLite or AI |
| Extraction schema | Broad string/number/null definitions | Date format/pattern, bounded vehicle and note lengths, fuel enum, positive liters/amounts, and non-negative integer odometer |
| Fuel handling | Free-form extracted fuel string | Enum of `etanol`, `gasolina comum`, `gasolina aditivada`, `diesel`, or `null`; prompt normalization plus a deterministic ethanol alias mapping |
| Unknown message | Longer explanation of available actions | `Não entendi a solicitação.` |
| Public export | Previous 24-node snapshot | Refreshed 27-node snapshot, no pinned event data or private sender ID, and `active: false` |

The extraction descriptions now give more explicit instructions for relative dates, preserving pending values, decimal/thousands formatting, and avoiding inferred amounts. The existing extraction system prompt is unchanged. The required-field code adds only the mapping of `Etanol`, `álcool`, and `alcool` to `etanol`; it still checks missing fields separately from the schema constraints.

Node positions were updated to match the new canvas. Existing registration, correction, confirmation, cancellation, and query paths remain connected after the new gates. Model selections, workflow settings, and SQL statements are unchanged.

## Public Export Privacy

The private source is the ignored local `Abastecimentos.json`. Only `workflow/abastecimentos.sanitized.json` is intended for Git.

- Credential blocks, webhook IDs, root workflow ID/version/metadata, and instance identifiers are removed.
- Pinned Telegram data is replaced with an empty `pinData` object.
- The configured sender ID is replaced with `REPLACE_WITH_TELEGRAM_USER_ID`.
- The public workflow is inactive, and its node IDs and connections are preserved.
- Runtime credentials and the original export stay private.

## Upgrade And Configuration

1. Keep a private backup of the current workflow and SQLite database.
2. Import the sanitized export into n8n and leave it inactive while configuring it.
3. Reassign Telegram, Groq, and SQLite credentials. Keep the SQLite community node installed and the existing tables available.
4. In `Usuário autorizado?`, replace `REPLACE_WITH_TELEGRAM_USER_ID` with your Telegram sender ID as a string. This is the user's ID, not the bot ID, username, or chat ID.
5. Use a private conversation with the bot and review any existing pending record whose fuel falls outside the new enum. Confirm that it can be corrected or cancelled during testing.
6. Complete the runtime checklist below, then activate the validated workflow.

The placeholder cannot match a numeric Telegram sender ID, so leaving it unchanged prevents access to the fuel-processing path. The gate checks the sender only: it does not prevent that sender from using the bot in a group. Pending state remains keyed by chat, and fuel queries still read shared history without user partitioning.

No database migration or data rewrite is required. Historical fuel strings are not normalized retroactively by this update.

## Rollback

Import the sanitized workflow from `v1.0.1` and reconnect credentials. The SQLite schema is unchanged, so no schema rollback is needed. Returning to that version removes the sender authorization and text gate and restores the previous extraction rules; review access before activating it. Private backups remain necessary for restoring runtime data and credentials.
